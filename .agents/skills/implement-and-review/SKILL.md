# 实施与 Review 仓库变更（Implement and review repository changes）

本 Skill 负责从规则发现到本地验证、独立 Review、修复闭环以及已授权的 Draft PR
交付。Ordinary Delivery authority：Issue-backed Implementation 的普通交付权限由用户的执行请求建立；本 Skill
不会自行扩大到 Merge、Release 或其他集成权限。

## 主协调器（Primary orchestrator）

主协调器从规则发现负责到验证完成，并保持唯一 Primary Workflow。只加载适用的领域与
验证 Skill，不在此复制子系统细节。已有 CI 失败与发布任务分别由 `fix-github-actions`
和 `release-monorepo` 担任 Primary Workflow。

## 普通 Issue-backed 交付与 Review 闭环

当用户明确要求执行一个 Issue-backed Implementation，且没有更严格的用户指令、
Issue Contract、AGENTS.md 或 applicable Skill 限制时，Top-level Codex Session 应
在用户已授予的范围内自主完成普通交付链；本 Skill 本身不授予任何远程权限：

```text
Inspect -> Branch / Worktree -> Implement -> Focused Validation
-> Complete Diff Review -> LOCAL READY -> Commit -> Push -> Draft PR
-> Structured Handoff -> AO Native exact-head Review -> Worker repair/new-head review
-> exact-head Remote CI -> Integration Readiness
```

普通交付链可以执行已获授权的 commit、push、Draft PR、Structured Handoff 和当前 PR head
的 CI observation；不得把这些事实推导为
Enqueue Merge Queue、Merge、Auto-merge、Publish、Tag、GitHub Release、Branch
Protection/Ruleset、Secrets 或 Repository Settings 权限。用户始终保留
Integration / Release authority，更严格的指令优先。普通交付不自动修改或读取回验
GitHub Project；只有当前用户明确要求 Project 操作时才执行。

所有 Development PR 均需 AO Native Reviewer 对 current exact HEAD 审查；Issue Risk、High hard rule 与四个 Review Signals 决定审查深度与权限证据，而不选择第二个 Reviewer。AO feedback 由原 Worker 独立核实并有界修复。PR 后 Review 缺失或未验证不追认 `LOCAL READY`，但阻止 `MERGE READY`。

## 1. 规则发现（Rule discovery）

1. 在仓库根目录运行 `git ls-files '*AGENTS.md'` 或等价的 Git-tracked 仓库内发现命令。
   只使用 tracked 结果，不扫描父目录、相邻仓库、其他 worktree、依赖树或 untracked 文件。
2. 对每个目标读取 root `AGENTS.md` 以及路径上更具体的 `AGENTS.md`。除非子规则明确
   override，否则祖先规则仍适用。
3. 检查 Skill metadata、分类任务，并只读取选中的领域或验证 Skill。
4. Git discovery fails 时 report a blocker。Do not fall back to a filesystem scan.
   适用规则确实冲突时停止受影响修改并报告冲突，不得声称两个互斥规则均已满足。

## 2. 任务分类（Task classification）

从 Core/compiler、generator、plugin、CLI、MCP、CI/workflow、release、documentation
或 repository infrastructure 中选一个主要领域。仅当请求跨越边界时增加次要领域。
按 root 路由表选择；领域 Skill 提供专门工作流：

- CLI command: `add-cli-command`
- read-only MCP Tool: `add-mcp-tool`
- MCP Prepare/Apply: `add-mcp-write-tool`
- plugin: `add-openapi-plugin`
- generated-output regression: `fix-codegen-regression`
- OpenAPI semantics: `upgrade-openapi-support`
- generated-output validation: `run-codegen-tests`

纯解释、只读诊断、摘要、状态检查或 Prompt 编写不使用本 Skill。已有 CI 失败交给
`fix-github-actions`，发布准备交给 `release-monorepo`。

## 3. 范围锁定（Scope lock）

编辑前运行：

```sh
git status --short
git rev-parse HEAD
```

普通写任务默认要求 clean worktree。若有既存改动，记录每条路径并分类为相关、无关
或重叠。不得自动删除或覆盖。只有用户明确授权且写入所有权不重叠，或使用 clean isolated
worktree 时才继续；目标路径重叠时需先取得对合并内容的授权或改用 clean worktree。

本地 Git 操作已获授权且路径与分支安全时，优先为无关的既存改动使用独立 worktree。
不得删除别人的 worktree、覆盖分支、prune worktree，或未经授权删除该独立 worktree。
记录路径与分支；无法安全隔离时停止并报告 blocker。

将生成或临时文件视为无害前，核对 Git ignore 状态、创建者及其对测试和 diff 的影响。
缺少 clean/isolated worktree 时，task-base-to-current-tree 是可能包含既存改动的
combined diff；按初始状态分开路径，不得声称整个 combined diff 均由 Agent 创建。

随后记录：

- the immutable task base SHA from `git rev-parse HEAD`;
- the initial branch, working tree, and staged state;
- objective and explicit non-goals;
- planned and prohibited directories;
- whether public APIs or generated bytes may change;
- Changeset decision;
- required and recommended validation;
- authorized external operations;
- `origin/main` only when the user authorized a fetch.

### GitHub 维护内容语言

创建 Development Issue、Draft PR 或 Structured PR Handoff 时，面向维护者的人类标题与
prose 默认使用中文，可采用 `type(scope): 中文说明`。代码、路径、命令、API、SHA、
contract marker、稳定 status token 和必要英文工程术语保留原样。此规则通过 canonical
Issue/PR template 与 `maintain-pr-handoff` Supporting Skill 落地；本 Skill 不复制第二套
PR body schema，也不因语言调整而改变 evidence、authority 或 merge/release boundary。

新发现的工作分类为 `required now`、`related follow-up` 或 `unrelated`。只有
`required now` 可进入当前 diff；重大产品范围或外部操作扩张需另行授权。不得用
`origin/main` 替换 task base：任务可能有意从现有 feature branch 或未合入 commit 启动。

### Changeset decision

- Public package 的用户可见修复、功能或 breaking change 应添加有意义的 Changeset。
- 纯 CI/test、内部重构或无用户可见 package 影响的文档变更可省略，并记录具体理由。
- 不得为了通过检查添加空 Changeset。
- Version Packages PR 消费现有功能 Changeset，不添加新的功能 Changeset。

## 4. 执行计划（Execution plan）

保持一份简短计划，覆盖调查、实施、聚焦测试、完整 diff review、P0/P1 修复、重新验证
与最终报告。编辑前重新运行 `git status --short` 并保留用户改动。

### Delegation Decision

计划后区分 `immediate critical path` 与 `independent, bounded sidecar investigation`。
`primary agent handles an immediate blocker`，并自行处理紧密耦合的下一步；只有不阻塞
下一步且主 Agent 能 `continue useful, non-overlapping work` 时，才委派只读调查。
`Zero investigation Subagents is valid`，通常 `ordinarily use at most one`；更多代理
仅用于 `genuinely independent questions`，必须有界，并保证 `no duplicate task delegation or unbounded fan-out`。
`Do not dispatch an immediate blocker and then wait idly`；不得把紧急阻塞项派出后空等。

主 Agent 是唯一主要写入者，负责最终集成、验证与报告。调查代理仅返回证据和建议；采纳前
主 Agent 重新读取共享文件。调查代理 `no default write authority`；root `AGENTS.md` 中的
例外要求 `explicit user authorization for non-overlapping write scopes`。代理
`never edit the same file concurrently`，并且 `delegation remains one level`。
调查代理不能替代 AO Native PR Reviewer。Reviewer 不参与 planning 或 implementation；
它在 Draft PR 后审查 current exact HEAD，不能参与 PR 前的本地实施门。

## 5. 实施（Implementation）

完成最小而完整的变更：新行为添加行为覆盖，bug 修复添加回归测试。不得弱化断言、删除
失败测试、机械接受 snapshot、升级无关依赖、大范围格式化或重构无关架构。生成结果缺陷
应在 owning source 修复。

## 6. 聚焦验证（Focused validation）

将检查分类为：

- `required`：进入 readiness 前必须通过；
- `recommended`：环境与影响合理时运行；
- `not applicable`：写明理由；
- `SKIPPED`：相关但未执行，并写明理由。

从当前 manifest 和更具体规则中选择最小充分证据，典型映射如下：

| Change | Evidence |
| --- | --- |
| Documentation | repository/document contract, links or formatting |
| One package | package test, typecheck, build as applicable |
| Generated output | focused fixture, complete semantic/file-set review, consumer validity, byte-stable second run |
| MCP | affected unit/integration/stdio/write/recovery layer and Doctor when registration changes |
| CI/workflow | focused script test, repository contract, local CI-equivalent command |
| Cross-package/shared infrastructure | affected tests plus root build, typecheck, and Vitest |
| Release | `release-monorepo` gates; never publish implicitly |

未执行的命令不得记为 `PASS`。

## 7. 完整 Diff Review（Full diff review）

实施与初步测试后重新读取：

```sh
git status --short
git diff --stat
git diff --check
git diff
git diff --cached --check
git diff --cached
git diff --stat "$TASK_BASE_SHA"
git diff --check "$TASK_BASE_SHA"
git diff "$TASK_BASE_SHA"
git ls-files --others --exclude-standard
```

只有暂存区为空时可略过 cached 命令。task base 命令始终用于检查 task-base-to-current
working tree；即使普通 staged/unstaged diff 为空也必须执行。审查完整任务 diff，
不能依赖记忆中的编辑。

将每个 untracked 结果分类为任务创建、既存或意外。读取内容前先检查路径、类型和大小，
避免无界读取二进制或过大文件。完整读取每个任务创建的 untracked 文本文件，并检查正确性、
安全、测试、文档、凭据、临时数据和绝对路径。未核实的意外文件或未审查的 untracked
文件阻止 `READY`；只有已核实、无害且已解释的测试输出例外。不得默默忽略或自动删除。

提交前只暂存明确授权的路径：

```sh
git add -- <authorized-path-1> <authorized-path-2>
git diff --cached --stat
git diff --cached --check
git diff --cached
```

每次 commit 以及后续 Git 或远端 mutation 后，重新读取：

```sh
git status --short
git branch --show-current
git rev-parse HEAD
git log -1 --oneline
git diff --stat "$TASK_BASE_SHA"..HEAD
git diff "$TASK_BASE_SHA"..HEAD
```

提交后再次发现 untracked 文件并完整审查 task-base-to-HEAD diff，覆盖已提交新增文件和
提交之外的意外文件。任务树变化使用双点 task-base-to-HEAD diff，不用三点 merge-base
diff 替代。若工作树仍脏，继续检查 task-base-to-current working tree。提交后工作树
干净并不能证明完整任务 diff 已被审查。

检查：

- 正确性：需求、边界、错误、异步/并发、平台、状态、退出码与确定性；
- 架构：归属、依赖方向、已有抽象与重复实现；
- 兼容性：public API、CLI、配置、生成结果、支持的输入与 Node/平台；
- 安全：路径、命令、不可信输入、凭据、权限、写入与竞态；
- 测试：回归和反例、行为断言与关键 mock；
- 文档：行为、命令、限制与一致性；
- Git 范围：意外文件、lockfile、Changeset、生成/临时输出与无关格式化。

## 8. AO Review 与有界修复（AO review and bounded repair）

PR 前的 `LOCAL READY` 只要求 focused validation、Changeset 决策、Implementer Complete Diff Review、Git 范围与安全检查。记录 Issue Risk、High hard rule 和四个 canonical Review Signals，用于 AO 审查深度及 High 权限证据门；所有 Development PR 统一走 AO Native Review，没有 Reviewer Selection 或 structured skip。

### AO exact-head gate

Draft PR 创建并 readback Handoff 后，由 AO Native Reviewer 对 current exact PR HEAD 完成独立审查。只有 AO runtime 或其他可验证持久来源能提供的 Run ID、身份、状态、reviewed SHA、verdict、结构化 findings 才算证据；无法导出时写 `UNVERIFIED`。`APPROVED`、`CHANGES_REQUESTED`、`BLOCKED`、`UNVERIFIED` 是稳定判定；运行中、失败、stale HEAD、P0/P1 unresolved 均不能进入 `MERGE READY`。AO internal verdict 不等于 GitHub-native Approval，若保护规则要求原生 Approval，另行核验。

High / Root of Trust 必须有真实 freshness/context separation、Shell/FS 有效只读及 MCP/GitHub Tool Surface 无写权限证据。Prompt、TOML 或模型文字不足以证明；证据缺失时保持 `NOT MERGE READY`，不切换 Reviewer。候选修改 Root of Trust 时，immutable task-base policy 仍适用于本候选；新规则仅在受保护集成后适用于后续任务。

### Feedback and repair

AO finding 和 GitHub comment 分别记录来源、reviewRunId/commentId、head SHA、投递状态与解决状态。Worker 只处理属于当前 PR 的反馈，并独立验证每条 finding；confirmed in-scope P0/P1 必须修复，out-of-scope P0/P1 是 blocker。未证明反馈已投递给 Worker，不得声称 Worker 已处理。每次修复完成后重跑受影响验证、完整 diff review，最多三轮自动修复；预算耗尽或仍有 P0/P1 时停止并报告 blocker。

Push 新 HEAD 立即使旧 AO review、Handoff、CI、受影响本地验证失效。Worker 重新绑定 Handoff、请求或等待 AO 对新 HEAD 的 Run，并核实真实完成状态；同一 Run/HEAD 的 feedback 和 GitHub write-back 幂等，不重复评论。AO 与旧 ChatGPT Work event task 不得对同一 HEAD 同时做代码审查写回；旧任务停写未核实则阻止写回和集成，外部任务配置需单独授权。

## 9. 已授权的远程交付（Authorized remote handoff）

contract-id: ordinary-delivery-authority
contract-id: local-only-boundary
contract-id: user-controlled-integration
contract-field: ordinary-delivery=issue-backed-request
contract-field: local-only=remote-writes-denied
contract-field: integration=user-controlled

Ordinary Delivery authority：Issue-backed Implementation 的普通交付权限在 `LOCAL READY` 后包含 exact task diff 的 Commit、Push、Draft PR、Structured Handoff 与 exact-head CI observation；明确 local-only 或 read-only 时 remote writes remain unauthorized。本 Skill 不授予 Merge、Merge Queue enqueue、Auto-merge、Publish、Tag、GitHub Release、Ruleset、Branch Protection、Secrets 或 Settings 权限。

只暂存已授权路径，审查 staged diff；Commit 后重读 task-base-to-HEAD diff、状态与 untracked files。Push reviewed SHA，创建 Draft PR 并调用 [`maintain-pr-handoff`](../maintain-pr-handoff/SKILL.md) 建立 canonical Handoff，安全传输 body、readback、验证 head binding。Draft PR 即可进入 AO Native Review。`Ready for Review` 只在 PR 仍 Open、无 Manual Hold/阻塞反馈、Handoff 已回读且 local reviewed SHA = pushed SHA = current PR HEAD 时才转换；先核实旧 Work event task 不会因 `ready_for_review` 对同 HEAD 再次写 Review。转换本身不代表 AO Review、CI PASS 或 `MERGE READY`；如果当前授权或单写入者状态不清，保持 Draft。

查询 required CI 的 current-head SHA；PENDING、FAILED、UNVERIFIED 与 PASS 分别报告，不把 Local PASS 或 AO verdict 当作 CI PASS。Review 或 CI 证据变化后 refresh、readback Handoff。`MERGE READY` 仍须另行只读核验最新 main、Shared Surface、依赖、AO exact-head Review、required CI、GitHub protection、Manual Hold 与所有 P0/P1。Merge / Release remains user-controlled；用户始终是 Integration / Release authority。

## 10. 完成门（Completion gate）

- 所有改动在授权 scope；初始 clean 或已隔离既存改动。
- focused validation、Complete Diff Review、`git diff --check` 已通过；所有 staged、unstaged、task-base-to-current-working-tree、task-base-to-HEAD 与 untracked 文件已检查。
- 每个 task-created untracked 文本文件已完整读取，意外文件已解释。
- Issue Risk、High hard rule 与四个 signals 已记录；没有已知未解决 in-scope P0/P1。
- 已授权远程交付时，local reviewed/pushed/PR head SHA 匹配，Handoff readback 通过，current-head AO/CI 状态如实报告；任何缺失证据不声明 `MERGE READY`。
- 最后一次修复后重新验证并 review complete diff；每次 Git mutation 后重读最终 status、branch、HEAD、log 和 task-base-to-HEAD diff。

报告精确命令及 PASS/FAIL/SKIPPED、剩余风险、变更文件、Changeset 决策、外部操作、最终 branch/HEAD/status；区分 `LOCAL READY`、`REMOTE CI`、`MERGE READY`、Merge 与 post-merge DONE。
