# openapi-to 4.0.0-rc.0 release candidate

`4.0.0-rc.0` is the first 4.0 release candidate. Its purpose is to validate the
versioned package graph, package surfaces, installation paths, generation
contracts, and MCP safety model before a stable 4.0 release. It is not a stable
or production-readiness declaration.

## 当前 RC remote policy 更新

后续 RC 的 Remote Loader 改为 Node 原生 fetch：explicit HTTP(S) roots 为 caller-authorized，
derived cross-origin `$ref` / redirect 需 allowedHosts，移除旧 private-network switch 与 DNS/IP checks。
以下 rc.0 描述是历史 release contract；当前行为以 [migration guide](../migration-v4.md) 为准。

## Highlights

- A compiler pipeline with structured diagnostics, deterministic artifacts,
  validation, inspection, contract diffing, dry-run, and check modes.
- Multiple named microservice Targets with repeatable CLI `--target`
  selection and managed or Workspace output bases.
- Local JSON/YAML/YML and bounded HTTP(S) inputs with restrictive redirect,
  host, private-network, and portable-path policy.
- A complete `openapi-to` installation entrypoint that supplies `openapi`,
  `openapi-to`, and `openapi-to-mcp`.
- An independent `@openapi-to/mcp` package with server and
  `@openapi-to/mcp/cli` APIs.
- Target-scoped operation catalog, search, contract summaries, projections,
  and persistent additive selection.
- MCP modes with 3 analysis Tools, 8 trusted-config read-only Tools, or 10
  Tools when the operator enables the Prepare/Apply controlled writer.
- Transaction-backed generation with output locks, ownership manifests,
  bounded one-time plans, stale-state rejection, rollback, and crash recovery.

## Breaking and security-sensitive changes

The 4.0 major line makes several fail-closed behaviors contractual:

- private-network remote input is denied by default;
- configured headers are cleared on cross-Origin redirects and HTTPS-to-HTTP
  redirect downgrades are rejected;
- artifact path and case collisions fail instead of depending on write order;
- cleanup deletes only unchanged files owned by the prior manifest;
- unsafe native/portable path forms are rejected consistently;
- CLI failures use classified non-zero exit codes.

See [Migrating to openapi-to 4](../migration-v4.md) for examples and migration
guidance.

## Installation for RC testing

After the RC is published under the approved prerelease dist-tag, use an
explicit tag rather than the unqualified package name:

```sh
pnpm add -D openapi-to@rc
```

Advanced MCP-only consumers can use:

```sh
pnpm add -D @openapi-to/mcp@rc
```

The repository preparation phase does not publish either command or change the
`latest` dist-tag.

## Validation scope

The RC candidate is required to pass:

- build, package and project-reference typechecking, Vitest, and tracked-file
  lint;
- A1 contracts and CommonJS, ESM, and local HTTP CLI E2E;
- MCP unit, integration, stdio, controlled-write, recovery, complete, and
  Doctor gates;
- repository contract, package-surface, Changesets, and pack-install release
  checks;
- tarball manifest/content inspection and clean external consumers;
- Node 20 minimum-runtime coverage and a newer maintained Node runtime.

The detailed evidence belongs in
[4.0.0-rc.0 validation](./4.0.0-rc-validation.md).

## Known limitations

- OpenAPI 3.2 is compatible-read with diagnosed generation gaps, not complete
  support.
- One controlled-write plan covers one Target and one output root.
- Node.js filesystem transactions reduce but cannot eliminate same-user TOCTOU,
  abrupt power-loss, or weak network-filesystem semantics.
- Trusted configuration and plugins execute with the authority of the Node.js
  process.
- The MCP server is stdio-only and does not provide HTTP transport,
  authentication, Resources, Prompts, Tasks, Apps UI, or background jobs.

## Deferred

- Stable 4.0 publication
- Large real-world OpenAPI A2 evaluation
- CLI operation-level selective generation
- Cross-Target Apply
- Complete OpenAPI 3.2 generation support
- Automatic service discovery and OpenAPI merging

Report RC feedback and reproducible failures through the
[GitHub issue tracker](https://github.com/Vc-great/openapi-to/issues). Include
the candidate version, Node version, operating system, command or MCP mode, and
sanitized diagnostics; never attach credentials, configured headers, or
private document contents.
